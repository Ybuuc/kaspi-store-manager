## Backup SQLite (перед изменениями)

Из остановленного старого каталога, в котором существует файл базы:

```powershell
New-Item -ItemType Directory -Force backups
python -c "import sqlite3; s=sqlite3.connect('file:instance/kaspi-store-manager.sqlite3?mode=ro',uri=True); d=sqlite3.connect('backups/pre-release.sqlite3'); s.backup(d); assert d.execute('PRAGMA integrity_check').fetchone()[0]=='ok'; d.close(); s.close()"
```

Использовать новый backup-каталог для каждого релиза; не перезаписывать предыдущую копию.
Сохранить секрет и конфигурацию отдельно, с прежними правами доступа.
После backup сверить размер, время, контрольные количества записей и возможность чтения.

  сначала сохранить текущую БД, затем восстановить backup при остановленных процессах.
  Учесть заказы/изменения после backup и согласовать их повторный ввод.
- [ ] Запустить старую версию с прежним секретом, проверить integrity и бизнес-smoke.
- [ ] Сверить количества/остатки, открыть доступ, наблюдать 15 минут.
- [ ] Зафиксировать rollback как новую фактическую доставку предыдущего SHA;
  failed deployment связать с incident. Закрыть incident после подтверждения восстановления.
- [ ] Внести `issue_number` и `deployment_id` в `data/incidents.json`;
  подтверждать `complete` только за реально проверенный интервал.
- [ ] На следующий день разобрать причину, добавить regression test и обновить чек-лист.

Цель восстановления сервиса (RTO): 15 минут. Допустимая потеря данных (RPO): 0
при откате кода с актуальной БД; при восстановлении backup — до момента копии,
с отдельной сверкой и восстановлением операций. Это цели, не подтверждённые SLA.
Плановый drill проводится на копии тестовой БД, фиксируется фактическая длительность;
его результат нельзя выдавать за реальный MTTR команды.
