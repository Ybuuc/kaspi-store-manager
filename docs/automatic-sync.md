# Стабильная синхронизация API и XML

Настройки совместимы со старым `.env`: прежний `KASPI_SYNC_INTERVAL_SECONDS`
принимается, но новые независимые часы определяются следующими параметрами:

```dotenv
KASPI_AUTO_SYNC=1
KASPI_API_SYNC_INTERVAL_SECONDS=300
KASPI_XML_SYNC_INTERVAL_SECONDS=1800
KASPI_XML_MAX_BACKOFF_SECONDS=21600
```

Старый ключ сохранён для старых клиентов конфигурации. Если новых параметров
нет, применяются API=300 и XML=1800; сохранённый срок следующей попытки не
сбрасывается изменением настроек или перезапуском. Для временного выключения
автоматических задач задайте `KASPI_AUTO_SYNC=0`. Ручное чтение также соблюдает 429.

## Устройство и восстановление

Один существующий координатор просыпается раз в 5 секунд. API выполняется в
отдельном процессе, XML — в одном ограниченном по времени потоке с собственным
Playwright. Общая SQLite `sync_schedules` содержит отдельные строки api/xml:
даты, блокировки, число отказов, cooldown, последний результат и heartbeat.
Атомарный claim исключает параллельный экспорт между Gunicorn workers;
уникальный orders slot исключает второй импорт API. Таблица добавляется без
изменения/удаления существующих записей. Старое расписание XML переносится при
первом создании строк. `boot` не делает будущий срок немедленно наступившим.

После аварийного завершения XML lease истекает через 10 минут. API worker
сохраняет прогресс/heartbeat; без heartbeat 10 минут его старый слот может быть
восстановлен. Следующий запуск повторяет идемпотентное чтение, не списывает склад.
Закрытие веб-сервера не обрывает уже работающий отдельный API-процесс.

429: поддерживаются `Retry-After` в секундах и HTTP-дата. При отсутствии заголовка
применяется exponential backoff с положительным jitter, до 6 часов для XML и
до часа для API. Явный более долгий срок Kaspi соблюдается полностью. Нулевой/
прошедший Retry-After даёт минимум 1 секунду; немедленного повтора нет.
Cooldown записывается до возврата ошибки и проверяется перед каждым запросом,
в ручном API-запуске и ручном экспорте. Успешный цикл сбрасывает backoff.
401/403 не повторяются внутри запроса. Сеть, timeout, 500/502/503/504 — максимум
3 попытки одного неудавшегося запроса, с задержкой 1/2 секунды + jitter. Другие
постоянные ошибки не повторяются. Успешный запрос не отправляется заново.

Составы заказов читаются максимум четырьмя запросами вперёд. После 429/401/403
очередь прекращается, незапущенные Future отменяются; уже принятые до отказа
данные остаются в SQLite. Отдельные ошибки в заказах оставляют статус partial.
Неизменённые подтверждённые архивные составы кэшируются до 24 часов.

## Каталог и сверка

TLS, проверка продавца/даты XML, read-only allowlist и атомарная публикация
сохранены. Неуспешный trigger, включая 429, не разрешает принять старый файл
как новую выгрузку. Дата XML никогда не заменяется текущим временем. Физический
склад, закупка, резервы и движения не вычисляются из stockCount/предзаказа.

Перед закрытием браузера снимаются и завершаются route-обработчики
(`unroute_all(behavior='wait')`), затем закрываются context и browser.
Ожидаемая ошибка закрытия подавляется только в фазе cleanup. Неожиданное
закрытие при работающем экспорте — interrupted; сетевые ошибки не скрываются.

При отличающемся SKU продавца публичный master code не объединяет варианты.
Подтверждённое сохранённое наблюдение API можно сверить без новых HTTP-запросов:
`reconciliation.repair_saved(apply=True)`. История с реальными StockMovement/
OnwayItem или складскими флагами защищена; без точных SKU автоматической
привязки нет. 225 старых заказов — архивный формат без подтверждения новым
API-импортом; его наличие не доказывает отсутствие SKU или ошибку API.

Панель показывает независимые интервалы, попытки, полностью успешные циклы,
последние полученные данные, следующую попытку, причину задержки, счётчики,
обратный отсчёт и использование сохранённых данных. Ошибки обезличены:
нет имён, телефонов, order code, токенов и подписанных URL; для корреляции — HMAC ref.

## Запуск Windows

```powershell
cd C:\kaspibot
.\tools\local-catalog.ps1 start
.\.venv\Scripts\python.exe app.py
```

Локальный HTTPS-сервер запускается отдельно: `tools/local-catalog.ps1 start`.
Вход в отдельную сессию, когда нужен: `python tools/kaspi_catalog_login.py`.
В режиме разработки не запускайте одновременно `app.py` и `flask run` на одном
порту. Открытая вкладка браузера не нужна для фоновых задач.

## Linux / подготовка Azure

Azure и платные ресурсы этой задачей не создаются. Используйте установленный
в Docker bundled Chromium (`KASPI_CATALOG_BROWSER_CHANNEL=chromium`), headless,
TLS и постоянный том с SQLite и `.local-catalog` (включая собственную сессию/CA).
Базу можно задать абсолютным `KASPIBOT_DATABASE`; её каталог должен быть доступен
на запись одному экземпляру приложения. SQLite не предназначен для нескольких
реплик на разных файловых системах. Для небольшого инстанса достаточно 1 worker.

```sh
python -m playwright install --with-deps chromium
gunicorn --bind 0.0.0.0:5000 --workers 1 --threads 2 --timeout 120 --graceful-timeout 120 wsgi:app
```

Не используйте `--preload`: координатор должен создаваться внутри worker.
Graceful shutdown ждёт ограниченную XML-задачу; API сохраняет данные по заказам,
после убийства контейнера слот восстанавливается по heartbeat. Публикацию сессии,
секретов, реальной БД и прайса в Git/Docker-образ исключают ignore-файлы.
Сессию Kaspi нельзя сделать бессрочной: когда Kaspi требует авторизацию, оператор
обновляет собственную сессию. Круглосуточность бесплатной Azure-площадки здесь
не подтверждалась и развёртывание не выполнялось.
