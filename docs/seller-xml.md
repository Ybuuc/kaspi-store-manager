# Сверка каталога продавца из XML

В приложении появился раздел **XML-каталог**: `/products/seller-catalog`.
Администратор может загрузить файл из кабинета продавца. Импорт требует входа
и CSRF; он не отправляет никаких изменений в Kaspi. JSON-снимок доступен
администратору в `/api/kaspi/catalog`.

CLI: `python -m flask --app app:create_app kaspi-import-xml "путь/ACTIVE.xml"`.
Перед обновлением выполнить `init-db` и сохранить резервную копию `app.db`.

## Семантика данных

- Сохраняются неизменяемый исходный XML, SHA-256, продавец, дата внутри файла
  и время импорта UTC. Часовой пояс даты XML не выдумывается.
- `offer sku` — артикул продавца. `model`, `brand`, цены каждого города,
  код склада, `available`, `stockCount` и `preOrder` хранятся без потери смысла.
- `49.0` допустимо как целое количество 49; отрицательные, дробные, NaN,
  повторные SKU/склады/города и пустые прайсы отвергаются до изменения базы.
- Отсутствующее количество остаётся неизвестным. `available=yes` не означает
  одну штуку. При предзаказе stockCount не доказывает физическое наличие.
- Снимок ACTIVE не считается полным ассортиментом: отсутствующие товары
  не удаляются, не архивируются и не получают нулевой остаток.
- Прайс не содержит закупочную себестоимость. Он не используется для расчёта
  чистой прибыли и не переписывает старые физические остатки/резервы/onway.
- Цены снимка и локальной карточки подписаны отдельно. Разные города сохраняются
  отдельно; произвольная общая цена не выбирается.

## Привязка карточек

Импорт ищет точный SKU с учётом регистра. Название/alias не считаются
доказательством тождества вариантов размера/цвета. Для отсутствующего SKU
создаётся карточка с неизвестным физическим остатком и закупкой. Если точное
название уже занято, отображаемая подпись дополняется `[SKU ...]`; исходный
`model` без изменений находится в снимке. Старые карточки не переименовываются.

Наблюдение API с конфликтом перепривязывается по точному SKU из XML, только
если по этой строке ранее не создавались складские движения. В raw_json
сохраняются прежняя связь, причина и SHA файла, подтвердившего новую связь.
Сумма, количество, статус и состав заказа не меняются. Для свежих API-импортов
точный SKU также не отбирает публичный Kaspi ID, ошибочно занятый старой карточкой.

Повтор одного SHA не создаёт карточек или снимков. Снимок более ранней даты
и файл другого продавца отвергаются. Весь импорт выполняется одной транзакцией.

## Проверка предоставленной выгрузки

Файл получен 21.11.2026; дата внутри — **19.11.2026 22:07**.
В нём 365 уникальных SKU, числовое количество у каждой позиции, один склад
и один город цены. У 364 позиций ненулевой предзаказ. Это датированный снимок
заявленной доступности, а не доказанная инвентаризация склада на 21 ноября.

На копии базы разрешены 85 из 129 спорных позиций заказов. Оставшиеся 44 позиции
относятся к 13 SKU, которых нет в ACTIVE-выгрузке. Нужна дополнительная выгрузка,
содержащая эти артикулы, либо подтверждение их связи продавцом. Их отсутствие
не доказывает, что заказ выдуман или товар имеет нулевой остаток.
Из 365 SKU 52 уже имели точную карточку, 313 добавлены из настоящего XML.
Все 105 ранее существовавших карточек сохранены побайтно по исходным полям;
363 движения, 155 onway, aliases и история парсера не изменены.

129 старых активных заказов вне периода предыдущей API-проверки этим XML
не обновляются: прайс не содержит статусы заказов. Их проверка остаётся отдельной
задачей синхронизации API. База и XML передаются только локально пользователю,
в публичные GitHub, CI и образ Docker не включаются.

Локальный HTTPS с обязательной проверкой TLS: [local-https-catalog.md](local-https-catalog.md).

Если SKU отличается только регистром от старой карточки, импорт отменяется для ручной сверки: существующий уникальный индекс архива сохраняется, автоматическое объединение запрещено.
