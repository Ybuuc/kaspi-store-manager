# ЛЗ8: SoW, SLO/SLA и границы

Результат: архивное приложение с сохранённой app.db и US01–18, код, миграции,
тесты, документация. Приёмка: пользователь запускает комплект на копии данных,
вторая команда выполняет UAT, замечания заводятся в Issues, критические закрываются.
Scope changes: issue с причиной, оценкой, влиянием на данные; согласование заказчика.
Права: авторство исходных частей сохраняется; лицензия собственного репозитория
не определена. Перед распространением определить права владельцев; открытые
библиотеки остаются под своими лицензиями. Наличие исходников не означает open-source лицензию продукта.

| Сценарий | Целевой SLO | Измерение | SLA для учебного демо |
|---|---|---|---|
| Каталог | успешные чтения ≥99.5%, p95≤800мс при200VU | Locust + HTTP лог | Не договорное; при превышении остановить новые функции |
| Сохранение карточки | ≥99% успешных валидных операций, p95≤1.2с | API-нагрузка без внешних API | Исправление P1 до повторной демонстрации |
| Восстановление базы | integrity=ok и RTO≤60мин | Отдельная тренировка с таймером | Нет обещания до измеренной тренировки |

Error budget доступности: 30×24×60×(1−.995)=216 минут/30дней.
Для write-сценария бюджет ошибок —1% валидных операций, не216минут.
Система не измерялась месяц, SLO являются целями. Локальный бесплатный запуск
не объявляется соответствующим production-SLA. Бюджет и unit economics — finance/.

# ЛЗ11: стратегия тестирования и UAT

Unit: валидация цен/статусов/финансовых формул/прогноза. Интеграция: SQLite,
additive migration, роли/CSRF, оба интерфейса на одном products, аудит, parser worker.
UI: Playwright, фиктивная база отдельно от app.db. Нагрузка: tests/locustfile.py,
клиенты логинятся и читают каталог;200VU нельзя заменять тестом скорости одного клиента.
API: JSON запросы с session cookie и X-CSRF-Token. Mock внешних API не равен реальному Kaspi.
Данные: синтетические в CI; настоящая база только локально для проверки сохранности.
Uptime Kuma запускается профилем operations: http://localhost:3001;
добавить HTTP монитор http://web:5000/health. Демо-монитор ещё не настроен через UI.

## Runbook: восстановление единой app.db

1. Остановить web, parser workers и backup-сервис; запретить запись.
2. Сохранить повреждённую app.db и возможные -wal/-shm отдельно для диагностики.
3. На временной копии backup выполнить PRAGMA integrity_check; должно быть ok.
4. Подменить app.db проверенной копией, сохранить права пользователя сервера.
5. Запустить init-db новой версии, выполнить вход, каталог, aliases и отчёт.
6. Разрешить работу только после сверки данных; записать время/RTO и номер копии.
7. При ошибке не запускать старую схему поверх новой: вернуть согласованную пару код+backup.

`python tools/backup_archive.py --database app.db --output backups --interval-seconds 86400`
создаёт целостную копию раз в сутки, хранит30дней, пока процесс запущен.
Это RPO до24ч, а целевой RPO≤15мин требует интервала≤900сек и выделенного места.
Восстановление всех данных тестируется; утверждение RTO≤60мин требует реального замера.
