# ЛЗ 9 — Жұмыс процесі (Kanban тақтасы)

Бұл құжат [ADR-001](../../adr/ADR-001-delivery-model.md) шешімін нақтылайды: баған тізбегі мен
In Progress ≤ 2 лимиті сол күйінде қалады, қосымша Ready және Review лимиттері мен өту саясаттары енгізіледі.

Тақта: [GitHub Project #1](https://github.com/users/Ybuuc/projects/1), Status өрісі.

## 1. Бағандар және WIP-лимиттер

| Баған | Мағынасы | WIP-лимит | Неге |
|---|---|---:|---|
| Backlog | Идея / US, әлі дайын емес | — | Шектеусіз, бірақ тәртіппен сұрыпталады |
| Ready | DoR орындалған, спринтке алынған | 4 | Бір апталық capacity (~4,5 сағ) шегінде ғана міндеттеме |
| In Progress | Орындалуда | 2 | ADR-001 бойынша өзгеріссіз |
| Review | Орындалды, DoD тексерілуде | 2 | «Орындалды, бірақ тексерілмеген» жұмыс жиналмауы үшін |
| Done | DoD орындалды | — | |

Жалпы жұмыстағы (Ready-ден басқа In Progress + Review) элемент саны ≤ 4.

Тақтада WIP-лимитті автоматты түрде ұстайтын мүмкіндік жоқ (GitHub Projects v2), сондықтан лимит —
саясат бойынша: лимит толған болса, жаңа элементті алмас бұрын бар элементті келесі бағанға өткізу
немесе Ready-ге қайтару керек. Лимитті бұзу оқиғасы ретроспективада талқыланады.

Тақтаны бапта: Status өрісінің опциялары дәл осылай аталуы тиіс —
`Backlog`, `Ready`, `In Progress`, `Review`, `Done` (скрипт атауларды осылай оқиды).
Тақтаға тек task-issue-ларды қосыңыз/жылжытыңыз; parent US issue-лерін Ready/In Progress/Review/Done-ға жылжытпаңыз (WIP мен метрика бұрмаланады). Бағандар атауына WIP санын қоспаңыз, әйтпесе экспорт атауды танымайды.

## 2. Өту саясаттары (policies)

| Өту | Шарт |
|---|---|
| Backlog → Ready | DoR толық орындалған (төмен); спринт мақсатына қатысты; Ready лимиті (4) асып кетпейді |
| Ready → In Progress | In Progress < 2; басымдық бойынша ең жоғарыдан алынады (спринт мақсатына қатысты US бірінші) |
| In Progress → Review | Қабылдау шарттарының барлығы орындалған; өзгеріс `main`-ге PR арқылы дайындалған |
| Review → Done | DoD чек-листі толық; Review-де тұрған элемент ең ұзағы бірінші тексеріледі |
| Review → In Progress | DoD орындалмаса: issue-ге себеп жазылады; элемент кері қайтады, лимит қайта тексеріледі |
| Кез келген → Backlog | Спринт мақсаты өзгерсе немесе блокерді жою мүмкін болмаса, issue-ге себеп жазылады |

Блокер: issue-ге `blocked` белгісі мен себебі қойылады; блокерленген элемент In Progress лимитіне
есептеледі (жасырын WIP болмауы үшін).

## 3. Definition of Ready (DoR)

US Ready бағанына өтуі үшін:

- [ ] Атауы, «Кім ретінде / не істегім келеді / не үшін» форматындағы сипаттамасы бар
- [ ] Нақты өлшенетін қабылдау шарттары (Acceptance Criteria) жазылған
- [ ] Бағасы (сағатпен) қойылған және ≤ 2 сағ. Тақтадағы элемент — US-тің бір task-issue-і; US 2 сағ-тан үлкен болса (мысалы US-01 = 4 сағ), parent US issue Backlog-та қалады да, task-issue-ларға бөлінеді
- [ ] Тәуелділіктері анық (алдымен қай US/жұмыс керек) және олар Done немесе осы спринтте жоспарланған
- [ ] Epic және басымдық белгіленген
- [ ] Тексеру тәсілі белгілі (қандай тест / қандай сілтемелерді тексеру)
- [ ] Спринт мақсатына қатысы бар

## 4. Definition of Done (DoD)

Элемент Done бағанына өтуі үшін:

- [ ] Барлық қабылдау шарттары орындалған және issue-де әр шартқа белгі қойылған
- [ ] Оң және теріс сценарийлер тексерілген (нәтиже issue/PR-де жазылған)
- [ ] Код өзгерсе: тест өткен, `security-scans` workflow-ы (Trivy, gitleaks) қызыл емес
- [ ] Құжат өзгерсе: мазмұны мен барлық сілтемелері тексерілген
- [ ] Өзгеріс PR арқылы `main`-ге біріктірілген, PR сипаттамасы issue-ге сілтейді (`Closes #N`)
- [ ] README / backlog / ADR құжаттары қажет болса жаңартылған
- [ ] Critical defect жоқ
- [ ] Тақтада элемент Done статусына ауыстырылған (метрика осы оқиғадан есептеледі)

DoD-ты екінші адам тексермейтіндіктен (жоба жеке орындалады), PR шаблонындағы чек-лист
Review бағанындағы өзін-өзі тексеру ретінде қолданылады.

## 5. Спринт ырғағы

| Іс-шара | Қашан | Ұзақтығы | Нәтиже |
|---|---|---|---|
| Спринтті жоспарлау | Дүйсенбі (алғашқы күн) | 20–30 мин | Спринт мақсаты, Ready тізімі ([02-sprint-planning.md](02-sprint-planning.md)) |
| Жұмыс | Дүйсенбі–жексенбі | capacity ~4,5 сағ/апта | Done элементтері |
| Спринтті қарау (review) | Жексенбі | 15 мин | Мақсат орындалды ма, демо/дәлел |
| Ретроспектива | Жексенбі | 30 мин | **Дәл бір** өлшенетін әрекет ([03-retro-protocol.md](03-retro-protocol.md)) |

Capacity негізі: 7 сағ/апта × 0,65 = ~4,5 сағ ([team-raci-capacity.md](../../planning/lz5/team-raci-capacity.md)).

## 6. Метрикалар анықтамасы

| Метрика | Анықтама |
|---|---|
| Throughput | Спринт ішінде Done болған элемент саны |
| Cycle time | In Progress-ке алғаш кіруден Done-ға дейінгі күнтізбелік күндер |
| p85 | Элементтердің 85%-ы осы уақыттан тез аяқталады (nearest-rank) |
| CFD | Күн соңындағы кумулятивті санақ, баған жолақтары = сол бағандағы WIP |
| Тар орын | Орташа WIP/лимит ең жоғары баған + CFD жолағы кеңейіп бара жатқан баған |

Метрикалар тек `scripts/flow_metrics.py` арқылы тақтаның оқиғалар тарихынан шығарылады.
