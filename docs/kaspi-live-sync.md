# Исправление источника данных и синхронизации Kaspi

## Что было неверно

1. Запуск по инструкции не читал KASPI_API_TOKEN из .env, хотя он есть в исходном архиве.
2. GET /products использовался как предполагаемая полная выгрузка кабинета; подтверждённого контракта для этого в проекте не было. Отсутствие товара на такой выборке могло ошибочно деактивировать карточки.
3. Позиции привязывались преимущественно по SKU/alias, хотя все 59 старых SKU пустые, aliases только 39. Несопоставленные позиции пропускались.
4. Вариант basePrice × quantity не учитывался. Для многопозиционного заказа могла сохраняться сумма 0.
5. Сохранённые state/status, локальные onway, остатки и расчётные комиссии/доставка смешивались в один якобы актуальный результат.
6. После добавления общего аудита повторная синхронизация могла падать на сериализации datetime last_synced_at. Это исправлено и проверено повторным импортом.
7. В разделе «Все» раньше отсутствовали архивные заказы и другие способы доставки; теперь они видны в подтверждённой выборке.

Аудит исходной локальной базы:59 товаров,359 кэшированных позиций заказов;
отрицательных stock_qty нет, но у 23 карточек stock_qty−reserved_qty−onway_qty<0.
Это не доказательство отрицательного физического склада Kaspi. Старые поля не
обнулялись и не корректировались предположениями. Они остаются для сверки/backup.

## Достоверная цепочка чтения

- Заказы: GET /orders, все 6 состояний, страницы до 100; даты фиксированы на время окна.
- Интервал одного запроса≤14 дней; история до 366 дней разбивается на такие окна.
- Позиции: GET /orders/{id}/entries; проверяются ID, количество и сумма.
- Описание: GET /orderentries/{id}/product → /masterproducts/{id}/merchantProduct.
- Для сопоставления используются реальные SKU, публичный код Kaspi, aliases
  и однозначное нормализованное название; конфликт не решается случайным выбором. Настоящая позиция заказа сохраняется
  с отметкой конфликта, прежние связи и складские движения не меняются.
- Повторный импорт обновляет ту же позицию order_code::entry_id. История не создаёт
  повторных списаний/продаж и не пересчитывает старый физический склад.
- Новая карточка из заказа содержит настоящие полученные данные. Если склад или
  текущая цена предложения не получены, это unknown, а не придуманная доступность/цена.

Контракты: [список заказов](https://guide.kaspi.kz/partner/ru/shop/api/orders/q3201),
[позиции и цены](https://guide.kaspi.kz/partner/ru/shop/api/orders/q3203),
[master product](https://guide.kaspi.kz/partner/ru/shop/api/orders/q3207),
[merchant product](https://guide.kaspi.kz/partner/ru/shop/api/orders/q3208).
Это API заказов. Он не даёт оснований считать количество в заказах фактическим
остатком всего кабинета; закупочная себестоимость также не следует из продажи.
Полный каталог, текущие цены предложений и остатки требуют свежей выгрузки продавца
либо отдельно подтверждённого интерфейса доступа к этим данным.

## Что показывает приложение

В рабочем режиме главная, «В пути», отчёт Kaspi и сводный API используют только
наблюдения нового импорта source=kaspi_api. Старые 359 строк доступны отдельно как
«Сохранённые до сверки». Синтетических заготовок вместо ответа нет.
Выручка берётся из полученных COMPLETED-позиций. Чистая прибыль не объявляется
известной без подтверждённых закупки, комиссии и доставки. Комиссия 12% и старые
расчётные тарифы не выдаются за фактические расходы кабинета.
Старые учебные/расчётные функции сохранены; их интерфейс включается явно
KSM_DEMO_MODE=1 и не используется как источник живых данных.

Синхронизация запускается в отдельном процессе, чтобы большой кабинет не
обрывался по тайм-ауту веб-запроса. Статус, прогресс, время и ошибки видны на
странице заказов. Параллельный повторный запуск блокируется; ошибка API не
превращается в успешный пустой импорт. Чтение позиций ограничено 4 потоками,
записи SQLite выполняются последовательно. Данные HTTP-ответов и токен не
печатаются в журнал. В Kaspi отправляются только GET, статусы/цены не меняются.

## Запуск с реальным кабинетом

1. Сохранить backup всей текущей app.db.
2. Установить обновление и выполнить `python -m flask --app app:create_app init-db`.
3. Задать KASPI_API_TOKEN переменной окружения либо вручную скопировать свой
   токен из архивного .env в локальный .env рядом с app.py. Не добавлять его в Git.
   Переменная окружения имеет приоритет. KSM_SECRET_KEY задаётся как раньше.
4. `python -m flask --app app:create_app kaspi-check` — проверка реального GET без записи в базу.
5. «Kaspi-заказы → Базаны жаңарту» — фоновая загрузка; дождаться конечного статуса.
   Альтернатива: `python -m flask --app app:create_app kaspi-sync --days 14`.
6. При partial прочитать ошибки, не считать сверку завершённой. Старые активные
   заказы проверяются отдельно по коду, даже если вышли за 14 дневное окно.
7. Для окончательной сверки физического склада предоставить свежую выгрузку
   товаров/остатков именно из кабинета продавца. Данные копии архива этого не заменяют.

Проверка реального подключения 19.11.2026: токен из исходного архива вернул
HTTP200. В ходе проверки все 6 состояний дали более 400 заказов за 14 дней;
точные результаты и время завершения относятся к локальному отчёту запуска,
а не к этому статичному документу. Реальные записи и токен в GitHub не публикуются.
Тестовые фикстуры используются только в изолированных автотестах.
