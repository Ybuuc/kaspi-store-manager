# ADR-002: архивное приложение и одна app.db как основа

Статус: принято по явному указанию пользователя 19.11.2026.
Контекст: архив функционально богаче; исходная база содержит реальные данные.
Нельзя заменять её учебными таблицами или вести два независимых склада.
Варианты: (1) менеджер как основа + отдельная база бота, (2) архив как основа
и добавочные функции, (3) полное переписывание. Выбран вариант 2.
Вариант 1 отвергнут: два регистра и ручная сверка; вариант 3 — риск потери поведения.
Последствия: главные страницы и SQLAlchemy-модели из архива; старый менеджер
становится модулем /management на тех же products и stock_qty. Цена с точностью
до сотых сохраняется в добавленном price_cents, синхронизируется с current_price.
Учебные заказы — новая таблица demo_orders в том же файле; KaspiOrderSync не переименовывается.
Миграции только добавляют колонки/таблицы/индексы; исходные значения не исправляются автоматически.
59 исходных пустых SKU сохраняются; для новых ручных карточек SKU обязателен.
Оригинал базы и .env не публикуются в GitHub; пользователь получает локальный комплект с данными.
Риски: сырые SQL-операции и ORM используют один файл — операции должны быть короткими;
SQLite не считается доказанно готовым к 200 конкурентным пользователям.
