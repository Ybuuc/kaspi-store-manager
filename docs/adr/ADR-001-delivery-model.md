# ADR-001: Жеткізу моделін таңдау

Күні: 2026-09-20
Мәртебесі: Қабылданды
Жоба: Kaspi Store Manager

## 1. Контекст

Kaspi дүкенін басқару жүйесі тауарларды, бағаларды,
қойма қалдықтарын және тапсырыстарды есепке алуға арналған.

Жобаның бастапқы талаптары толық нақтыланбаған.
Функциялардың басымдығы прототипті тексеру және
пайдаланушылардың пікірін алу барысында өзгеруі мүмкін.

Жоба оқу жұмысы аясында шектеулі уақытпен орындалады.
Сондықтан негізгі функцияларды ерте көрсетіп,
жүйені біртіндеп толықтыру қажет.

Алғашқы MVP тауарды қосу, өзгерту, іздеу және қойма
қалдығын көрсету мүмкіндіктерін қамтиды.
Нақты Kaspi сервисімен интеграция MVP құрамына кірмейді:
ол қолжетімділік пен талаптар анықталғаннан кейін
жеке тапсырма ретінде қарастырылады.

## 2. Қарастырылған нұсқалар

### Нұсқа 1. Waterfall

Артықшылықтары:
- Кезеңдер мен құжаттар алдын ала анықталады.
- Жоспардың орындалуын бақылау жеңіл.

Қабылданбау себебі:
Талаптар әлі өзгеруі мүмкін. Толық жүйені соңында ғана
көрсету пайдаланушының маңызды ескертулерін кеш алуға
әкелуі мүмкін.

### Нұсқа 2. Scrum негізіндегі итерациялық жұмыс

Артықшылықтары:
- Қысқа спринттер арқылы жұмыс істейтін нәтиже алынады.
- Тапсырмалар мен кері байланыс жүйелі қарастырылады.

Қабылданбау себебі:
Жобаны бастапқыда бір студент орындайды.
Толық Scrum рөлдері мен іс-шараларын ұйымдастыру
осы кезең үшін артық ұйымдастырушылық жүктеме туғызады.

### Нұсқа 3. Kanban арқылы басқарылатын итерациялық-инкременттік жеткізу

Артықшылықтары:
- Тапсырмалардың орындалуы көрініп тұрады.
- Басымдықтарды жаңа ақпаратқа сәйкес өзгертуге болады.
- Бір мезгілде орындалатын жұмыстар санын шектеуге болады.
- Функциялар шағын, тексерілетін бөліктермен жеткізіледі.

Шектеулері:
- Мерзімдер мен басымдықтарды бөлек бақылау қажет.
- Нақты қабылдау шарттары болмаса, тапсырмалар созылып кетуі мүмкін.

## 3. Шешім

Kanban арқылы басқарылатын итерациялық-инкременттік
жеткізу моделі таңдалды.

Жұмыс бір апталық жоспарлау және нәтижені қарау
циклімен ұйымдастырылады. Дайын әрі тексерілген
функциялар шағын инкременттермен негізгі тармаққа қосылады.

Тапсырмалардың күйлері:
Backlog → Ready → In Progress → Review → Done.

In Progress күйінде бір уақытта екі тапсырмадан
артық болмауы тиіс.

Әр тапсырмада жұмыс сипаттамасы, түрі, басымдығы
және қабылдау шарттары көрсетіледі.

Тапсырма Done күйіне тек қабылдау шарттары орындалып,
нәтиже тексерілгеннен кейін ауыстырылады.
Код өзгерсе, оған сәйкес тексерулер орындалады;
құжат өзгерсе, мазмұны мен сілтемелері тексеріледі.

## 4. Шешімнің салдары

Оң салдары:
- MVP ерте дайындалып, оны тексеруге болады.
- Қателер мен талаптардағы сәйкессіздіктер ерте анықталады.
- Жұмыс барысы GitHub Projects тақтасында көрінеді.
- Жаңа талаптар басымдыққа сәйкес жоспарланады.

Теріс салдары:
- Барлық функциялардың аяқталу мерзімі бастапқыда дәл болмауы мүмкін.
- Тапсырмалар тізімі мен құжаттарды тұрақты жаңарту қажет.
- Бақылаусыз өзгерістер жобаның көлемін ұлғайтуы мүмкін.

Теріс салдарды азайту:
- MVP шекарасын README және тапсырмаларда бекіту.
- Әр тапсырмаға нақты қабылдау шарттарын жазу.
- Апта сайын басымдықтар мен нәтижелерді қайта қарау.
- Бір уақытта орындалатын жұмыстар санын шектеу.

## 5. Шешімді қайта қарау шарттары

Команда құрамы ұлғайса, тұрақты тапсырыс беруші пайда болса
немесе келісімшарттық шектеулер енгізілсе,
жеткізу моделін қайта бағалау қажет.
