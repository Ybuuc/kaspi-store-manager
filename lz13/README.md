# ЛЗ 13 · PM-ассистент Kaspi Store Manager

Каждый понедельник PM получает сводку PR, влитых в main за предыдущую календарную неделю (UTC+5). Источником служит GitHub REST, модель пишет короткий русский абзац, Python добавляет полный реестр со временем и ссылками. Решение подходит команде, которая готовит статус по изменениям кода. Статус доставки на сервер продавца требует отдельного подтверждения.

## Запуск команды

В GitHub откройте Actions → LZ13 PM digest. В проверочном PR и при ручном запуске workflow обрабатывает два исторических спринта. Артефакт pm-digest содержит report.md, source.json, вход facts-N.json, сырые ответы ollama-N.json и run.json. Черновик просматривает PM перед распространением. Тайм-аут, неполный ответ или сбой API дают ошибку запуска. Частичный артефакт годится только для диагностики.

После включения workflow в основную ветку расписание срабатывает по понедельникам в 07:17 UTC+5. Используется стандартный Linux runner публичного проекта и сервис Ollama на том же runner. API-ключ модели и постоянно включённый ноутбук не нужны. Для локального прогона установите Python 3.10+ и Ollama, запустите службу Ollama и выполните из корня проекта:

```shell
ollama pull qwen2.5:1.5b
python lz13/report.py --mode sprints --out results-sprints
python lz13/report.py --mode week --out results-week
```

Указывайте новое имя папки для каждого прогона. GITHUB_TOKEN необязателен для публичного проекта, в Actions передаётся временный токен только для чтения. Для повтора с сохранённым источником добавьте `--snapshot lz13/evidence/pulls.json`. Флаг `--facts-only` выполняет только сборку реестра для диагностики. Словарь TOPICS в report.py содержит одобренные темы по номерам PR этого проекта. Для нового PR ответственный может добавить безопасную короткую тему, иначе отчёт покажет «тема не размечена». Время разметки учитывается в активных затратах.

## Границы и трактовка

Спринт 1: 27.10.2026 00:00:00 — 01.11.2026 15:07:30. Спринт 2: 01.11.2026 15:07:30 — 15:24:00. Все границы по UTC+5, конец исключён. Используется merged_at, фильтр base=main. Источник дат: [фактический календарь проекта](https://github.com/Ybuuc/kaspi-store-manager/pull/61). Для ручной сверки откройте [PR проекта](https://github.com/Ybuuc/kaspi-store-manager/pulls?q=is%3Apr+is%3Amerged+base%3Amain). Три задачи Done во втором спринте и один влитый PR измеряют разные события. Длительность второго отрезка исключает прямое сравнение темпа двух командных недель.

## Данные и промпт

Шаблон находится в prompt.txt. Единственная подстановка — JSON с обозначением периода, числом PR, номерами и темами из словаря. Токен GitHub используется только для чтения GitHub. Запрещено включать в запросы модели ключи, пароли, cookies, заголовки авторизации, URL прайса продавца, базу app.db, логи заказов, телефоны и адреса покупателей, цены закупки, маржу, остатки и содержимое XML. Не копируйте описания PR, диффы, комментарии и названия веток в словарь тем. Исходный код приложения и данные магазинов для отчёта не требуются.

## Проверка и экономия

Для каждого предложения разобрать проверяемые утверждения: количество, номер PR, его тема, статус или эффект. Отметить верные утверждения, неточности и неподтверждённые выводы. Доля ошибок = (неверные + неподтверждённые утверждения) / все проверяемые утверждения. Отдельно отметить пропуски требований промпта. Хранить исходный текст рядом с исправленным. Проверять технический реестр отдельно от текста модели.

Для сравнения труда PM возьмите один и тот же объём (по короткой сводке для каждого спринта). Сначала составьте версию по GitHub самостоятельно, затем проверьте исходный ответ модели. Для независимого опыта лучше привлечь второго коллегу с сопоставимым опытом или поменять порядок на другой паре периодов. Время ожидания машины учитывается отдельно, если PM может в это время работать.

```shell
python lz13/review.py manual private-timing
python lz13/review.py review private-timing
```

Сохраните текст и замечания до остановки каждого таймера. Выход net_seconds — чистая экономия активного времени: ручное составление минус проверка с исправлениями минус прочие активные затраты. Отрицательное значение означает дополнительные затраты. Если PM ждёт окончания запуска, отдельно вычтите это время. Разовую разработку учитывайте при оценке окупаемости внедрения. Папку private-timing храните локально.
